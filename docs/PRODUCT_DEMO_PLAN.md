# 一、产品重新定义

## 1. 对外使命

不再优先使用：

> AI 自演进运行时 / 虚拟 AI Infra 团队 / 生命周期控制面。

这些表述可以保留在技术文档中，但不适合作为用户和投资人的第一句话。

对外第一句话统一为：

> **安装一次，以后本地 AI 自己测试和升级。**

第二句话解释产品行为：

> 当新的模型或加速方式出现后，系统先在本机真实测试；质量、速度和资源都更好才升级，失败就继续使用旧版本，原来的客户端和 API 不需要改。

## 2. 要抓住的具体痛点

不要再泛化为：

> 本地 AI Infra 很复杂，普通用户缺少专业团队。

首版只抓一个可感知、可演示、可以重复发生的痛点：

> **模型虽然能下载下来，但每次新模型、新加速方法或运行时更新出现后，用户仍要重新研究、部署、测试、判断和恢复。**

这一痛点的表现是：

- 一次部署可以交给 Codex、Ollama 或教程完成；
- 用户不知道哪个新能力适合自己的机器；
- “能启动”不等于“值得升级”；
- 速度提高可能伴随质量下降或内存上涨；
- 升级失败时，用户通常不知道如何安全恢复；
- 最终大量用户长期停留在旧模型、旧配置或默认配置。

产品要解决的不是第一次安装，而是安装后的持续生命周期：

```text
发现 → 本机测试 → 独立判断 → 无感升级 → 失败恢复 → 记住结果
```

## 3. 产品形态

第一阶段产品不是：

- 新的推理引擎；
- 模型聊天客户端；
- 通用 Coding Agent；
- 任意代码执行框架；
- 自研硬件；
- 支持所有模型与平台的“大而全”系统。

第一阶段产品是：

> **运行在本机、管理现有推理后端的自动升级系统。**

它可以把 MLX、llama.cpp、Ollama、DFlash2 或未来第三方 Runtime 当作候选能力，但核心价值不是发明这些技术，而是：

- 发现与当前环境兼容的候选；
- 在真实本机环境中公平测试；
- 用独立门禁判断是否更好；
- 保持稳定 API 完成晋级；
- 失败时恢复上一个已知良好版本；
- 将环境、实验与结果留在本地，供下一次复用。

# 二、当前事实基线

## 4. 已实现能力

当前代码已经具备：

### 稳定服务

- OpenAI-compatible API：`http://127.0.0.1:8000/v1`；
- 目标模型：`mlx-community/Qwen3.8-27B-4bit`；
- 当前 Recipe：`z-lab/Qwen3.8-27B-DFlash2`，native block；
- 本机 Dashboard：`http://127.0.0.1:9000`；
- 服务与控制面独立运行。

### 自演进内外环

- 当前部署模型生成并冻结实验计划；
- 可信候选 Manifest 与兼容性/资源预检；
- 固定 revision 下载、SHA-256 与 Candidate Store；
- Baseline 在线期间准备候选；
- Baseline 与候选使用相同 Serving 路径；
- 独立质量、性能、内存和错误门禁；
- 自动晋级、在线复验和失败恢复；
- Recipe Memory 与环境指纹；
- Watch、维护窗口、去重、退避和通知；
- 完整本地审计 Artifact；
- 167 项自动化测试通过。

## 5. 正式实机结果

环境：

- Apple M5 Pro；
- 48 GB 统一内存；
- Qwen3.8-27B 4-bit；
- MLX-VLM 相同 HTTP Serving 路径；
- 3 个 Benchmark Prompt × 每个 Prompt 3 次。

| 配置 | Generation TPS 中位数 | TTFT 中位数 | 峰值内存 | 质量门禁 | 相对 Baseline |
|---|---:|---:|---:|---:|---:|
| Baseline | 18.14 tok/s | 0.230 s | 16.449 GB | 4/4 | reference |
| DFlash2 block 6 | 35.31 tok/s | 0.194 s | 21.876 GB | 4/4 | +94.65% |
| DFlash2 native block 8 | 37.52 tok/s | 0.189 s | 21.725 GB | 4/4 | +106.84% |

用户可理解的结论应该写成：

> **我的本地 Qwen 发现了一项自己没有的推理能力；在质量检查通过后，它把输出速度从 18.14 提高到 37.52 tok/s，而我没有修改客户端和 API。**

同时必须说清楚代价：

- 峰值内存从 16.449 GB 增加到 21.725 GB；
- 提升仅对当前机器、模型、Runtime 和测试集成立；
- 不能外推为任意任务均稳定提升两倍；
- 后续仍需扩展不同输入/输出长度、并发、p95、接受长度及冷启动稳定性。

## 6. 当前产品化差距

核心闭环已经存在；Dashboard 产品叙事与完整外环接入已在 9 月 2 日完成第一版。当前剩余差距是：

1. 需要克隆仓库、创建 venv 并执行 `pip install -e .`；
2. 模型服务、Dashboard 和 Watch 需要分别启动；
3. launchd 目前只渲染配置，不负责安装和管理；
4. 首次 15 GB 目标模型下载缺少 GUI 进度、暂停、重试和存储位置选择；
5. 自治策略仍以 YAML 面向工程师；
6. 可信 Registry 当前是包内本地 Registry，尚无安全远程更新通道；
7. 仓库发布工程不足：大量未提交文件、无远程仓库/Tag、缺 LICENSE、CI、SECURITY、CONTRIBUTING 与安装包验证；
8. 还没有非作者从干净机器独立完成安装和升级；
9. p95、接受率、切换中断和多次冷重启证据仍待补齐；
10. 60—90 秒视频与完整无剪辑录像仍未制作。

这些工作比继续扩展新算法或新硬件更优先。

# 三、新版 Demo 只证明什么

## 7. 唯一核心命题

新版 Demo 只证明：

> **本地 AI 可以在不改变用户入口的情况下，自己验证并采用一项更好的推理能力。**

投资人或普通观众只需要记住五个结果：

1. API 没变；
2. 速度真实提高；
3. 质量门禁通过；
4. 失败可以恢复；
5. 用户没有参与技术判断。

## 8. Demo 不证明什么

当前不声称：

- 所有 Mac 都能获得两倍加速；
- 所有模型都支持 DFlash2；
- 系统已经能自动升级任意新 Target 模型；
- 完全无人监督地执行互联网代码；
- 已经替代专业 AI Infra 工程师；
- 当前版本已经适合生产服务器；
- 已经证明用户愿意付费。

## 9. 必须新增的用户级指标

除 TPS、TTFT、内存外，下一阶段必须开始记录：

| 指标 | 为什么重要 | 9 月 15 前目标 |
|---|---|---:|
| 稳定 API 保持率 | 证明上层应用无需重配 | 100% |
| 质量门禁 | 证明不是以质量换速度 | 4/4 全通过 |
| 回滚成功率 | 证明实验不会破坏长期使用 | 故障注入场景 100% |
| 人工决策次数 | 证明不是 Copilot | `evolve --once` 后 0 次 |
| 首次安装成功率 | 证明不是作者专用项目 | 至少 3 名陌生用户中 2 名成功 |
| Time-to-qualified-upgrade | 衡量一次升级完整时间 | 记录真实分段耗时，不先定目标 |
| 第二次复用收益 | 证明本地 Memory 有价值 | 至少展示一次跳过失败候选或优先复验 |

# 四、60—90 秒路演 Demo

## 10. 演示原则

完整正式演进需要数分钟，不能伪装成 60 秒实时完成。

因此准备两份材料：

### A. 完整无剪辑录像

真实展示：

```text
Baseline 正在服务
→ 发现可信候选
→ 安全准备
→ 生成并冻结计划
→ 公平实验
→ 4/4 质量门禁
→ 自动晋级
→ 原 API 在线复验
→ Memory 写入
```

要求：

- 保留真实时间戳；
- 不剪掉失败重试与维护窗口；
- 可以倍速播放，但明确标注倍速；
- 原始 Artifact 可供核验。

### B. 路演 60—90 秒精华演示

不重新跑完整五分钟实验，而是：

1. 回放一条已完成的真实正式演进证据；
2. 明确标注“历史真实运行回放”；
3. 在现场实时调用当前稳定 API；
4. 展示当前服务使用已晋级 Recipe；
5. 展示同一 API、质量 4/4、速度提升和 Previous Recipe 可恢复。

## 11. 建议分镜

### 0—10 秒：同一个入口

屏幕显示：

```text
Stable local API
http://127.0.0.1:8000/v1
```

用同一客户端发起请求，说明：

> 这是我一直使用的本地 Qwen，后面的升级不会要求客户端做任何修改。

### 10—25 秒：发现新能力

Dashboard 展示真实演进时间线：

```text
发现兼容加速能力
→ 来源与版本通过检查
→ 候选准备完成
```

对外不展示 Manifest、hash、revision 等细节，只显示：

- 来源可信；
- 与本机兼容；
- 资源在预算内；
- 旧服务仍在线。

### 25—45 秒：自己做实验

展示三组真实结果：

```text
Baseline             18.14 tok/s  质量 4/4
DFlash2 block 6      35.31 tok/s  质量 4/4
DFlash2 native       37.52 tok/s  质量 4/4
```

一句话说明：

> 模型提出实验计划，但质量和速度由独立程序判断，模型不能自己宣布自己变好了。

### 45—60 秒：无感升级

显示：

```text
升级成功
稳定 API：未改变
在线质量：4/4
旧配置：已保留
```

再次用原客户端请求，展示输出速度。

### 60—75 秒：失败恢复

不必现场破坏服务，可展示真实故障注入记录：

```text
候选启动失败 / 质量失败
→ 不晋级
→ Previous Recipe 恢复
```

### 75—90 秒：一句话结束

> **我没有教用户怎么配置 DFlash2；本地 AI 自己完成了发现、测试、判断和升级。**

## 12. Dashboard 改造

### 12.1 首页主叙事

首页上半部分改成三个用户可理解区域：

1. 当前本地 AI 正在运行；
2. 最近一次升级带来什么变化；
3. 下一次检查/升级状态。

首屏主按钮：

> **检查并升级本地 AI**

不要把“Planner”“Candidate Store”“Registry”等放在首屏。

### 12.2 增加完整演进接口

当前 `DashboardController.start_optimization()` 启动的是 `optimize`，无法展示完整外环。

建议新增：

```text
POST /api/control/evolve
GET  /api/evolution/current
GET  /api/evolution/events
GET  /api/watch/status
GET  /api/memory/summary
```

其中：

- `POST /api/control/evolve` 调用 `evolve --once`；
- `/api/evolution/events` 流式展示外环事件；
- `/api/memory/summary` 只返回脱敏汇总；
- 所有写操作继续使用同源 Session Token、二次确认和 workspace 锁。

### 12.3 增加证据回放模式

新增只读“真实运行回放”：

- 数据源为不可变 Evolution Artifact；
- 页面明确标注“历史真实运行”；
- 不修改服务；
- 不把回放动画伪装为实时实验；
- 可用于 60—90 秒路演。

### 12.4 下沉技术信息

以下内容放入“技术详情”折叠区：

- Manifest ID；
- revision；
- hash；
- Planner source；
-运行时版本；
- 原始 Artifact 路径；
- 内存和样本分布。

首屏只显示：

- 当前模型；
- 当前速度；
- 质量是否通过；
- API 是否稳定；
- 是否可恢复；
- 最近一次升级节省了什么。

# 六、开源、安装版与商业路径

## 13. GitHub 的角色

GitHub 是：

- 开发者预览；
- 开源信任；
- Issue 与贡献协作；
- 跨环境验证；
- Runtime、候选和验证器生态入口。

GitHub 不是：

- 面向纯小白的最终产品界面；
- 自动产生付费用户的商业模式；
- 替代安装包、自动更新和售后支持的渠道。

## 14. 产品分层

### 开源开发者版

- 单机 Mac；
- 稳定 API；
- 可信候选；
- 本机测试；
- 晋级/回滚；
- 本地 Memory；
- CLI 与基础 Dashboard。

目标：建立信任、获得真实场景和贡献者。

### 个人专业版（未来假设）

- 签名 DMG / Homebrew；
- 自动更新；
- 更丰富的受信候选源；
- 模型存储管理；
- 更好的通知与解释；
- 优先支持和稳定性保证。

目标用户：希望长期运行本地 AI，但不想成为 Infra 工程师的人。

### 企业服务器版（未来假设）

- Linux/NVIDIA 或企业服务器；
- 多环境与多服务；
- 私有 Registry；
- 团队权限、审批和审计；
- 企业业务评测门禁；
- 专家支持。

### Runtime / OEM 嵌入（未来假设）

与以下生态合作：

- Mac 本地 AI 工具；
- Ollama/llama.cpp/MLX 类 Runtime；
- NAS 与 AI PC；
- 模型管理器；
- 企业本地 AI 平台。

我们提供的是：

- 自动发现与实验；
- 独立验证；
- 稳定 API 晋级；
- 回滚；
- 本地经验；
- 可审计证据。

不提供硬件，不管理供应链。

## 15. 商业化原则

学习万格智元，但不复制其重资产路径：

- 免费和开源承担分发；
- 专业版、企业版、支持和生态授权承担收入；
- 不将用户原始轨迹默认上传或出售；
- 不依赖自营算力；
- 不通过自研硬件建立壁垒；
- 是否收费、谁付费，先由开源后的真实使用决定。

# 七、明确押注与舍弃

## 16. 当前押注

我们押注：

1. 本地部署 AI 会变得越来越普遍；
2. 模型与推理技术持续更新，用户不可能每次重新学习；
3. 一次性部署会被 Codex、Ollama 和教程商品化；
4. 长期发现、验证、升级和恢复可以形成独立产品；
5. 稳定 API、独立门禁和本地 Memory 会带来持续价值；
6. 推理引擎可以作为可替换后端，而不是必须自己拥有的资产。

## 17. 当前舍弃

9 月 15 日前不做：

- P5 新 Target 自动晋级；
- 自研重型推理引擎；
- Intel/AMD/NVIDIA/NPU 多平台扩展；
- 自营硬件；
- 通用聊天 App；
- 云端托管控制面；
- 更多投机解码算法；
- 企业权限与审计；
- 训练数据商业化；
- 结果分成或复杂定价。

原因：

> 当前最需要证明的不是“功能足够多”，而是“陌生用户是否理解、安装、信任并持续使用这条自升级闭环”。

# 八、发布后的验证问题

## 18. 产品价值验证

必须回答：

1. 用户是否愿意让软件长期驻留并检查更新？
2. 用户是否愿意让候选在本机下载和实验？
3. “更快但多占 5 GB 内存”是否仍被认为值得升级？
4. 用户是否理解系统为什么升级或拒绝候选？
5. 用户是否信任失败自动恢复？
6. 第二次演进是否比第一次更少测试、更少人工？
7. Codex 是否能以相同可靠性替代整个闭环？
8. 哪一类用户最依赖它：本地 AI 玩家、研究者、独立开发者还是小团队？

## 19. 继续门槛

开源后 4—8 周，若出现以下信号，继续投入：

- 至少 10 名陌生用户完成安装；
- 至少 5 次非作者机器上的完整演进成功；
- 至少 2 个外部贡献的候选/验证器/适配器；
- 自动升级相比手工流程明显减少用户决策；
- 用户愿意长期保留服务或主动询问专业版/服务器版；
- Recipe Memory 对第二次任务产生可测复用收益。

若出现以下情况，应收缩或修正：

- 大多数用户只需要一次部署；
- Codex 可同样稳定地完成发现、验证、升级和回滚；
- 用户不愿授权本地下载与切换；
- 每个候选都需要作者重新开发大量适配；
- Memory 不能减少后续搜索和人工；
- 安装和资源门槛使用户数量长期过小。
